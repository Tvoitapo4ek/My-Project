## 1. Состояние репозитория

  60 модульных тестов, сквозной автотест (~150 проверок, скриншоты).
* `TaskManager/` — посторонний Python-проект пользователя; не трогаю. Его
  workflow «Сборка» на Windows падает из-за кодировки — не наша зона.
* Git: ветка `claude/aetherwright-first-playable`, рабочее дерево чистое.

## 3. Сверка с «первым рабочим прототипом» (§21 промпта)

| № | Требование | Статус |
|---|---|---|
| 1–7 | персонаж, физика движения, камеры, сбор, инвентарь, блоки, крафт | ✅ |
| 8 | несколько функциональных механизмов | ✅ (плавильня, дробилка, верстак, ящик) |
| 9 | механическая передача | ✅ физически (шарниры, шестерни); ⚠ нет нагрузки/прочности/потерь |
| 10 | источник энергии | ✅ ячейка, динамо |
| 11–12 | магический источник, сбор и хранение | ✅ кристаллы → накопитель |
| 13 | передача магии **тремя способами** | ❌ сейчас один (связь накопителей) |
| 14 | магический потребитель | ⚠ динамо (через электричество), нет магического двигателя |
| 15 | рабочий магический эффект | ✅ импульс / левитация / разряд |
| 16 | аномалия и её стабилизация | ⚠ аномалия есть, стабилизации нет |
| 17 | визуальная логика: датчик + контроллер | ❌ |
| 18–21 | физпушка, сохранения, креатив, выживание | ✅ |
| 22–23 | бой, существа | ✅ базово (один вид существ) |
| 24 | диагностика механизмов и соединений | ✅ инженерные панели; ⚠ нет повреждений |

**Интеграционный сценарий** (источник → коллектор → накопитель → магический
двигатель → вал → производство → датчик + контроллер → неисправность →
диагностика → ремонт) сейчас проходит только до «накопителя» и «динамо».
Это главный пробел.

## 4. Технические риски

1. **Модель механической передачи.** Сейчас вращение передаётся физикой
   (моторы шарниров, ограничение скорости шестерён). Это честно (момент и
   нагрузка «настоящие»), но дорого: каждый вал — тело, каждая передача —
   ограничение решателя. Большие стационарные заводы так не потянуть, а
   передаточные числа, прочность и потери в физике выражать неудобно.
   → решение §6-A.
2. **Мир конечный и небольшой**; лиминальный масштаб и «острова» требуют
   стриминга и LOD (риск по памяти и времени ремешинга).
3. **Производительность тестовой среды**: программный рендер ~3 FPS; тест
   сборки тележки чувствителен к порядку систем (уже ловил регрессию).
4. **Сохранения**: новые сети (механика, магия, логика) должны сохраняться
   модульно — механизм `SaveHook` уже есть.
5. **Открытые вопросы концепта** (численные параметры, рунная логика,
   география) — заполняю только временными данными в RON с пометкой.

## 5. Предлагаемые подсистемы и зависимости

```
             ┌──────────── Signals (информация) ─────────────┐
             ▼                                               │
 Magic sources → Collector → Stabilizer/Filter → Storage → Transfer
                                                  │   (кабель │ руна-канал │ резонатор)
                                                  ▼
                                         Magic engine ─┐
 Electric: Cell/Dynamo → Wire network → Electric motor ─┼─► Kinetic network ─► Machines
 Physics bodies (вагоны, колёса) ◄── граница сети ─────┘   (вал/шестерня/редуктор/муфта)
 Damage/Wear → у каждого компонента;  Diagnostics/Overlays → читают все сети
```

Три вида взаимодействия разделены типами: **физическое** (Avian, кинетическая
сеть), **энергетическое** (электросеть, магическая сеть), **информационное**
(сигналы). Каждая сеть — свой модуль с графом, данными в RON и `SaveHook`.

## 6. Решения, требующие согласования

**A. Механическая передача (влияет на архитектуру).**
* *Вариант 1 — гибрид (рекомендую):* закреплённые на сетке валы, шестерни,
  редукторы, муфты и ремни образуют **кинетическую сеть-граф**: скорость и
  направление по передаточным числам, баланс момента (источники против
  нагрузки и сопротивления) → замедление и остановка, предел прочности →
  поломка самого слабого звена, потери. На границе с физическими телами
  (колесо на шарнире, пропеллер, поршень) сеть прикладывает настоящий момент
  через мотор шарнира и получает назад реальную скорость. Свободные
  физические сборки (телеги, корабли) продолжают работать на физике.
* *Вариант 2 — только физика* (как сейчас): всё честно, но тяжело для
  больших заводов и сложно для редукторов, ремней и прочности.

**B. Порядок работ.** Рекомендую начать с вертикального среза
интеграционного сценария (этапы V1–V5 ниже), а визуальную технику по
референсам (атмосфера, формы блоков, стриминг) вести следом.

**C. Утверждённые, но ещё не сделанные пункты** — смерть со сгустком и
точкой возрождения, кислород, архетипы маг/оборотень. Предлагаю после V5.

## 7. Вертикальные этапы

Каждый этап: код + данные в RON + сохранение + модульные тесты + шаг
автотеста + отладочный оверлей + отчёт по форме §26.

* **V1 — Кинетическая сеть** (по решению A): вал, шестерни малая/большая,
  редуктор, муфта, ремень; скорость/направление/момент/нагрузка/потери/
  прочность; табло оборотов; дробилка работает от вала; оверлей передач.
* **V2 — Электросеть**: мощность против запаса, провода с пропускной
  способностью и потерями, перегрузка, электромотор.
* **V3 — Магический конвейер**: коллектор, фильтр, стабилизатор,
  накопитель с типом/стабильностью/искажением; передача тремя способами
  (проводник, рунный канал, резонатор-передатчик/приёмник) с дальностью,
  потерями и совместимостью; магический двигатель → кинетическая сеть;
  базовая модель рун (направление, фильтр, ограничение) как настройка
  устройств.
* **V4 — Логика**: сигналы отдельным графом; датчики (обороты, заряд,
  предмет, игрок рядом), кнопка, рычаг, таймер, сравнение, И/ИЛИ/НЕ,
  контроллер с командами механизмам; оверлей сигналов.
* **V5 — Повреждения, диагностика, ремонт** механизмов + сквозной
  автотест интеграционного сценария (все 10 шагов).
* **V6 — Аномалии**: генератор (только в раздражённой среде, вероятностный
  результат), стабилизатор (удержание, предсказуемость, предупреждения),
  последствия потери контроля; одна временная или гравитационная аномалия.
* **T4 — Техника визуала и мира** (из `ART_DIRECTION.md`): формы блоков из
  данных, атмосфера/туман/bloom, стриминг чанков и LOD.
* Далее G-этапы мира и персонажа (сгусток смерти, кислород, архетипы,
  жидкости, транспорт с аэродинамикой и плавучестью, генерация лиминальных
  территорий, башня) — по одному, с согласованием содержания.
